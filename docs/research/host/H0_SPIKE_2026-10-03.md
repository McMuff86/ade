## Experiment 1 — Secret Service für einen Host-Prozess (R5)

### Befund zur Schlüsselbund-Konfiguration (nur gelesen)

- Anmeldung per SDDM-Autologin (`/etc/sddm.conf.d/autologin.conf`), PAM-Kette
  `sddm-autologin` mit `pam_permit` und `pam_gnome_keyring` (`auto_start`).
- `~/.local/share/keyrings/Default_keyring.keyring` liegt im
  **unverschlüsselten** gnome-keyring-Format (Dateikopf `[keyring]`, nur
  Dateirechte 0600). Inhalte wurden nicht gelesen. Deshalb ist der Schlüsselbund
  nach dem Autologin ohne Passwort „entsperrt“; einen Entsperr-Wettlauf gibt es
  auf diesem Rechner nicht. Das ist bestehender Zustand und betrifft heute schon
  den `safeStorage`-Schlüssel der Desktop-App; der Host-Entscheid ändert daran
  nichts.
- `gnome-keyring-daemon` ist ein socket-aktivierter systemd-User-Dienst
  (`gnome-keyring-daemon.socket` in `sockets.target`, Dienst selbst nicht
  enabled). Zusätzlich ist `org.freedesktop.secrets` über
  `/usr/share/dbus-1/services/` D-Bus-aktivierbar.

### Reihenfolge beim Booten (aus Journal und `critical-chain` der laufenden Sitzung)

| Ereignis (User-Manager-Zeit) | Zeitpunkt |
|---|---|
| `dbus.socket` → `dbus-broker.service` bereit | @340 ms → @357 ms |
| `basic.target` erreicht | @357 ms |
| `gnome-keyring-daemon.service` aktiv | @363 ms |
| `default.target` erreicht | @9.735 s (Wartezeit durch `rclone-googledrive.service`) |

Eine Host-Unit mit `WantedBy=default.target` startet nach `basic.target`
(Standard-Ordering für Dienste). Der Keyring-Daemon war in dieser Sitzung
6 ms nach `basic.target` aktiv. Fehlt er zum Startzeitpunkt noch, startet
die erste Anfrage ihn per D-Bus-Aktivierung.

### Messungen

| Fall | Umgebung | Ergebnis |
|---|---|---|
| Kein Secret Service | privater D-Bus ohne Dienstverzeichnisse | `unavailable` nach 5 ms: „org.freedesktop.secrets was not provided by any .service files“ |
| Entsperrt | privater D-Bus, eigener Daemon mit Passwort-Schlüsselbund | Speichern, Lesen, Löschen ok unter Node (16 ms) und `ELECTRON_RUN_AS_NODE` (12 ms) |
| Gesperrt, Schreiben | wie oben, Sammlung per `Lock` gesperrt | Fehler „unlock prompt was dismissed“ (Node und Electron) |
| Gesperrt, vorhandenen Eintrag lesen | wie oben | Fehler „unlock prompt was dismissed“ |
| Gesperrt, **nicht vorhandenen** Eintrag lesen | wie oben | **kein Fehler, Ergebnis `null`** |
| Echter Session-Bus aus transienter User-Unit | `systemd-run --user --unit=ade-host-spike-keyring`, `ELECTRON_RUN_AS_NODE=1` | Lesen 9 ms; eigener Eintrag gespeichert, gelesen und gelöscht in 30 ms; cgroup `app.slice/ade-host-spike-keyring.service` |

### Folgerungen für H2 (Vorschlag, noch kein Vertrag)

1. Ein Host unter systemd und `ELECTRON_RUN_AS_NODE` erreicht den Secret Service
   mit `@napi-rs/keyring` und `linux.store: 'secret-service'` (kein
   Kernel-Keyring-Rückfall). Der Kandidat aus E8 ist tragfähig.
2. **„Eintrag fehlt“ ist bei gesperrter Sammlung nicht von „gibt es nicht“ zu
   unterscheiden.** Der Host darf einen fehlenden Wrapping-Key daher nie als
   Erststart deuten (neuer Schlüssel, erneute Migration), ohne vorher die
   Eigenschaft `Locked` der Zielsammlung über D-Bus abzufragen. Gehört als
   Negativkontrolle in H2.
3. `secrets: unavailable` ist sauber erkennbar (sofortiger Fehler).
4. Der Host soll nicht von Unit-Ordering abhängen: Beim Start den Zustand
   bestimmen, bei `unavailable`/`locked` mit Backoff erneut versuchen und
   `NameOwnerChanged` für `org.freedesktop.secrets` beobachten.
5. Die Schutzwirkung des Wrapping-Keys entspricht auf diesem Rechner nur den
   Dateirechten, weil der Schlüsselbund unverschlüsselt ist. Das ist eine
   Benutzerentscheidung (Autologin), die ADE nicht ändern soll. ADE könnte sie
   in der Diagnose sichtbar machen.

### Vorfall während der Messung

Der erste Versuch im privaten Bus war nicht isoliert. Die geerbte Variable
`GNOME_KEYRING_CONTROL` und die systemweite D-Bus-Aktivierung führten dazu,
dass ein Test-Daemon den echten Daemon (PID 1943) kontaktierte. Der echte Daemon
protokollierte nur „The Secret Service was already initialized“.

Unmittelbar danach geprüft und unverändert:
- Schlüsselbund-Dateien (Zeitstempel 2. Oktober)
- Sammlungen `session` und `Default_keyring`, beide `Locked=false`
- keine neue `login`-Sammlung
- Alias `default`
- Daemon PID 1943

Wiederholt wurde mit `env -i`, eigener Bus-Konfiguration ohne
Dienstverzeichnisse und eigenem Laufzeitverzeichnis.

### Aufräumen

- Transiente Unit mit `--collect` entfernt; `systemctl --user status
  ade-host-spike-keyring.service` meldet „could not be found“. Es wurde nie
  eine Unit-Datei angelegt und nichts enabled.
- Private Busse, Test-Daemons und Wegwerf-Verzeichnisse beendet bzw. gelöscht;
  kein übrig gebliebener Prozess.
- Echter Schlüsselbund: 0 Einträge mit `service=ade-h0-spike`. Die Datei wurde
  durch Speichern und Löschen des Testeintrags neu geschrieben (neuer
  Zeitstempel 10:12:46, unveränderte Grösse 2436 Bytes).

### Ungeprüft, braucht einen Neustart bzw. eine andere Anmeldung

- Verhalten einer **enabled** Host-Unit bei einem echten Bootvorgang. Die
  Reihenfolge oben stammt aus dieser einen Sitzung.
- Schlüsselbund **mit Passwort** und ohne Autologin, also Entsperren durch PAM
  bei der grafischen Anmeldung. Das wäre auf anderen Rechnern der Normalfall.
- Windows (DPAPI) und macOS: nicht gemessen.

## Experiment 2 — node-pty unter `ELECTRON_RUN_AS_NODE` im gepackten Build

**Gepackter Build:** `electron-builder 26.15.3 --linux dir --x64` direkt
aufgerufen, nicht über `package:linux:dir`, weil dieses Skript `pnpm build`
ausführt. Eingabe war das vorhandene `out/` der persönlichen Instanz (nur
gelesen; Zeitstempel von `out/main/index.js` vorher und nachher 2. Oktober
12:51:14). Ausgabe ins Scratch-Verzeichnis, `electronDist` aus `node_modules`,
`npmRebuild: false` wie in `package.json`. Ergebnis: `linux-unpacked/ade` mit
`resources/app.asar` und
`app.asar.unpacked/node_modules/node-pty/build/Release/pty.node`. Das
Repository blieb sauber.

Hinweis: In dieser Shell hat der mise-Shim für pnpm keine Version;
electron-builder ruft pnpm intern auf. Gelaufen ist es mit
`MISE_PNPM_VERSION=9.15.9` nur für diesen Aufruf, ohne Änderung der
mise-Konfiguration.

**Prüfcode:** `scripts/spikes/h0/pty-probe.mjs` löst `node-pty` so auf, wie ein
Host-Einstieg innerhalb von `app.asar` es täte (`createRequire` relativ zu
`app.asar/package.json`), startet `/bin/cat` in einer PTY und misst 200
Rundreisen Schreiben → Echo.

| Fall | Ergebnis | Echo p50 / p95 / max |
|---|---|---|
| gepacktes `ade`, `ELECTRON_RUN_AS_NODE=1`, aus `app.asar` | ok; Auflösung innerhalb von `app.asar`, native Datei aus `app.asar.unpacked` | 0,046 / 0,094 / 1,39 ms |
| dasselbe in transienter User-Unit `ade-host-spike-pty` | ok | 0,040 / 0,092 / 1,42 ms |
| Checkout, Electron-Binary, `ELECTRON_RUN_AS_NODE=1` | ok | 0,053 / 0,095 / 1,67 ms |
| Checkout, Node 26.8.2 | ok | 0,043 / 0,103 / 3,78 ms |
| **Negativkontrolle:** gepackt mit `ELECTRON_NO_ASAR=1` | scheitert wie erwartet: „Cannot find module 'node-pty'“ | — |

**Folgerungen:**
- E2 ist für Linux belegt: Der Host kann mit dem ausgelieferten `ade`-Binary im
  Node-Modus laufen und node-pty aus dem gepackten Build laden, auch unter
  systemd. Die RunAsNode-Fuse ist im gepackten Build aktiv. Ihre bekannte Folge
  steht in E2.
- Die Echozeiten messen nur die PTY-Zeilendisziplin im selben Prozess. Sie sind
  **keine** Tastendruck-Latenz der Oberfläche; die misst Experiment 4.
- Windows (ConPTY, NSIS-Paket): nicht gemessen.

**Aufräumen:** Unit mit `--collect` entfernt („could not be found“). Der
gepackte Build liegt nur im Scratch-Verzeichnis der Sitzung.
